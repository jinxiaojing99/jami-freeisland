## 4. 为什么不能直接"拉新版覆盖"——三个硬障碍

| # | 障碍                                             | 后果                                                                    |
| - | ---------------------------------------------- | --------------------------------------------------------------------- |
| 1 | 三端源码**均无 `.git`**，是下载快照                        | 没有共同祖先，无法 `git merge`/`git diff`，一旦覆盖旧源码，F-904 改动**不可恢复**（除非靠本清单手工重建） |
| 2 | daemon 有源码树外的 **MinGW 构建补丁**                   | 升级 daemon 源码后，补丁上下文行号变化可能 `patch` 失败，导致 Windows 编译不过                  |
| 3 | daemon 16→17 改了 SWIG/API（`ExposedService` 改名等） | Qt/Android 客户端绑定的 daemon 接口若不同步，可能编译失败或运行时行为变化                        |

## 5. 推荐合并方案：先落袋、再重放（不做就地覆盖）

### 5.1 总策略

```
① 当前快照（含 F-904） → git init + 全量提交 → 打 tag freeisland-0.01-A6（版本控制兜底）
② 把 F-904 改动导出成 patch（以"原始快照"为基准）
③ 下载上游新版源码 → 独立目录 git init → 切到目标 tag/commit
④ 把 F-904 patch 重放到新版基线 → 解冲突 → 编译 → 全量回归
⑤ 新旧两套并存验证通过后，才决定切换；旧版保留至少两个版本周期
```

### 5.2 分组件执行顺序（建议 daemon → Qt → Android）

**第一步：给三端快照做版本控制（最高优先级，与升级无关，立即做也无损）**

```bash
# 对每个 jami-src/<repo> 目录
git init
git add -A && git commit -m "freeisland baseline: F-904 v0.01 (PC build6 / A6)"
git tag freeisland-0.01-A6
```

> 这一步把"当前可工作的状态"永久固化。做完之后再谈升级，任何操作都能 `git diff` / `git checkout` 回滚。

**第二步：导出 F-904 patch**

- 已有本次调研的逐文件清单（§3）。若要生成机器可读 patch，用"原始快照"作对照：Lite 做法是把 §3 中的**新增文件整份另存**，修改文件用 `git diff` 从"去掉 F-904 的版本"生成——但更稳妥的是：**先按 §5.1 建好 git 基线后，从 GitHub 下载同版本原始快照作为 base，再 `git diff --no-index base current > f904.patch`**。

**第三步：daemon（风险最低，可单独先做）**

| 动作       | 要点                                                                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 目标       | 上游 master `5de24595`（17.0.0），或等下一个 stable tag                                                                                                                                      |
| 操作       | 全新目录拉取源码 → 逐个重试 `jami-build/patches/` 下的 MinGW 补丁（context 变了就手工修）→ 单独编译 daemon 验证                                                                                                  |
| **必须验证** | `grep` 确认 `JamiAccount::sendTrustRequest`、`ContactList` 的 `active 联系人自动 confirmed`、`conversation_module.cpp` 的 `cloneConversationFrom` 这三处逻辑与 F-904 依赖的行为**未变**——这是"名片加好友后能通讯"的命根子 |
| 回滚       | daemon 独立，出问题直接切回 16.0.0 源码重编                                                                                                                                                      |

**第四步：Qt 客户端**

| 动作  | 要点                                                                                                                 |
| --- | ------------------------------------------------------------------------------------------------------------------ |
| 目标  | 建议**先对齐 stable/20261110.0**（最小变更、易验证），而非直接 master                                                                  |
| 操作  | 新目录拉 tag → `git apply f904_qt.patch` → 预期冲突集中在 `JamiStrings.qml`、`SettingsView.qml`、`qml.qrc`（三方都改过资源/UI 索引时）→ 手工解 |
| 保留项 | 构建号机制（`generate_version_info.cmake` + `version_info.*` + `AboutPopUp.qml`）必须从旧版带过去，让构建号从 6 继续递增                    |
| 验证  | `qmllint` 全部新增/修改 QML → 编译 → About 显示 `V0.01.7` → F-904 全链路（§6）                                                    |

**第五步：Android 客户端**

| 动作  | 要点                                                                                                                                      |
| --- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 目标  | 若 daemon 升到 17，Android **必须**同步到含 `update for daemon APIs` 的 master（`7e8edd73` 之后），否则接口不匹配                                              |
| 操作  | 新目录拉源码 → apply F-904 patch → 冲突预期在 `HomeActivity.kt`（上游改了 home 逻辑）、`strings.xml`（两边都加字符串）、`AccountService.kt`（若上游改了 addContact 签名）→ 手工解 |
| 保留项 | `addContactFromCard` 的确定性选边逻辑（字典序小的一端发 TR）、self 守卫、剪贴板 3 秒防重、版本标记（顺手把 `freeisland_version` 升 A7）                                        |
| 验证  | `assembleNoPushDebug` → 装机 → About 显示 A7 → F-904 全链路（§6）                                                                                |

| 序 | 用例                              | 判定                       |

## 7. 备选策略（按需求取舍）

| 策略                  | 做法                 | 优点                   | 代价 / 适用                       |
| ------------------- | ------------------ | -------------------- | ----------------------------- |
| A. 原地冻结（本次推荐执行）     | 什么都不升，只建 git 基线    | 零风险，F-904 刚验收通过，保护成果 | 拿不到上游修复；**适合当前无迫切需求**         |
| B. patch 重放（本方案 §5） | 新版源码 + F-904 patch | 吃到全部上游更新             | 需完整回归一次；冲突需手工解                |
| C. 选择性 cherry-pick  | 只挑安全的小修复           | 风险最小                 | 收益有限，daemon/客户端版本仍不匹配         |
| D. 就地覆盖             | 新版直接覆盖旧源码          | 快                    | **禁止**：无 .git，F-904 改动会丢，不可恢复 |
