## 1. 需求定义（源自三场景分析）

### 1.1 场景还原

| 场景 | 节点构成 | 结论 | 依据 |
|---|---|---|---|
| ① | A 有公网 IP + B 对称 NAT | 能通信：A 把公网候选交给 B，B 直接连 A，绕开 TURN | `ice_transport.cpp:1123-1143` 生成 srflx 候选；DHT 交换候选 |
| ② | **A/B 均对称 NAT + C 公网普通节点** | **当前不能**：A↔C、B↔C 各自能直连，但 C 不转发 A↔B | 源码无 peer 转发逻辑（见 §4.1） |
| ③ | A/B 均对称 NAT + C 跑 TURN 服务 | 能通信：C 代收转发 | `connectionmanager.cpp:1971-1995` TURN 配置链 |

**F-905 要填补的正是场景②**：让一个**普通的、同构的、有公网可达性的 Jami 节点 C**，在会话级临时承担 A↔B 的数据中转，使两个对称 NAT 私网节点无需 TURN 服务器即可收发消息。

### 1.2 一句话定义

> **任何节点都能按需临时充当"数据中转站"：A、B 各自与 C 直连，C 在两条连接间转发密文字节；C 下线即换人或回退，不依赖任何特定节点常在线。**

### 1.3 明确不做什么

| 不做 | 原因 |
|---|---|
| 不做成独立服务程序 / 常驻进程 | 违反硬约束 1（见 §3） |
| 不修改 TURN 协议（RFC 5766）或复用 `turn.jami.net` | F-905 的价值就是**去中心化中继**，走 TURN 等于没解决 |
| 不引入第一个"必须在线"的中继节点 | 违反硬约束 1 |
| 不改变消息签名/commit 格式（ADR-001） | 属协议变更，旧节点不兼容，须单独拍板 |

## 2. 本质定位：与四种通信方式对比

| 维度 | 直连（ICE host/srflx） | TURN 中继 | **F-905 对等中继** | 动态超级节点 |
|---|---|---|---|---|
| 中转者 | 无 | 中心服务器（coturn） | **普通 Jami 节点** | 无（仅作 DHT 引导/问路） |
| 是否同构 | — | ❌ 专化角色 | ✅ 所有节点同能力 | ✅ 节点同构 |
| 是否常开 | — | ❌ 必须常在线 | ✅ 临时、可下线 | ✅ 临时 |
| 部署额外进程 | 否 | ✅ 是 | ❌ 否 | ❌ 否 |
| 中转内容可见性 | — | 服务端可见（除非 DTLS） | **可做到仅密文字节**（见 §4.3 路线 A） | 不中转数据 |
| 依赖特定节点 | 否 | ✅ 依赖该 TURN | ❌ 可替换 | ❌ 可替换 |
| 合规（硬约束 1） | ✅ | ❌ 场景化例外 | **条件合规**（守 §3 三条红线） | ✅（已定稿） |

**核心区别**：TURN 是"部署一台专门服务器、大家依赖它"；F-905 是"任何节点都能临时搭把手、它走了换一个"。前者是中心化设施，后者是同构节点的按需协作——这正是 F-905 能否绕过硬约束的关键。

## 3. 硬约束合规分析（本章为整个功能的成立前提）

### 3.1 逐条核验

| 硬约束 | F-905 的潜在风险 | 合规设计（必须落实） | 判定 |
|---|---|---|---|
| 禁止锚点/常开节点/服务器/额外进程 | C  looks like 一台中继服务器 | C 是普通 App 内能力，不单独部署、不常驻；会话结束即释放 | ✅ 可满足 |
| 节点完全同构 | C 被特化为"中继角色" | **中继能力内置于所有节点**，人人可当，非专属身份 | ✅ 可满足 |
| 可随时上下线 | A/B 依赖 C 在线 | C 下线 → 重选中继或回退；**正确性不绑定特定 C** | ✅ 可满足 |
| 不允许正确性依赖某节点常在线 | 把 C 写成固定中转 | 中继是会话级临时选择，多候选 + 故障切换 | ✅ 可满足 |

### 3.2 三条设计红线（违反任一条即退回为"场景化例外"，等同自建 TURN）

1. **能力同构**：中继逻辑编译进每一个客户端，任何节点都能当，不产生"中继专用版"。
2. **临时按需**：中继按会话建立、随会话释放，不是 7×24 常驻服务；不设置"专职中继节点"配置。
3. **可替换、可回退**：任一中继失效不得导致通信永久中断——重选其他可达节点，或在无候选时明确失败/回退 TURN（回退 TURN 时须在规格里标为例外，不得宣称纯 P2P）。

> 结论：**守住三条红线时 F-905 与硬约束 1 相容**，语义等同已定稿的"动态超级节点"。若产品要求"固定几台公网节点永远在线当中继"，那就是场景化例外，必须在规格 v3 明示、不得宣称纯 P2P。此分界请用户在第 7 章 Q1 拍板。

### 4.3 两条技术路线（关键分叉，对应第 7 章 Q2）

| 路线 | 做法 | 中转者可见性 | 端到端签名/加密 | 难度 | 合规 |
|---|---|---|---|---|---|
| **A（推荐）传输层字节中继** | A↔B 仍建端到端 TLS，C 只在两条 ICE 通道间转发**密文字节**（应用层 TURN，但节点同构） | C 只见密文，看不到正文 | 完整保留 | 高：受 `TlsSocketEndpoint` 只收 `IceSocketEndpoint` 限制，须新增中继端点类型或扩展 ICE 支持三方 | ✅ 最佳 |
| B（不推荐）Git 仓库中转镜像 | A 把签名 commit 推到 C，C 供 B fetch | **C 可见明文 commit**（本地仓明文落盘） | 签名在，但机密性破环 | 中：改动集中在 `conversationrepository.cpp` | ⚠️ 需在 commit 层另加端到端加密才能补救 |

> 路线 A 保住"中转者看不到内容"，是 F-905 相对 TURN 的核心卖点；路线 B 与本地仓明文落盘的现状叠加，会让任意中继节点读到你全部消息，除非补做 F-902 类加密——而 F-902 当前暂缓。

### 4.4 路线 A 可行性深挖（2026-11-20 22:0x 源码核准，已验证）

用户拍板路线 A 后，对"难度高"的核心难点做了逐层源码核准，结论：**可行，且有比预期更干净的插入点**——无需让 TLS 端点直接吃裸 UDP。

| 层 | 类型 / 签名 | 是否局限于 ICE | 源码依据 |
|---|---|---|---|
| 连接建立（两处） | `make_unique<IceSocketEndpoint>(ice, ...)` → `make_unique<TlsSocketEndpoint>(std::move(endpoint), ...)` | ✅ 顶层封装钉死 ICE | `connectionmanager.cpp:867,876`（connectDevice）、`:1554,1560`（DHT 请求） |
| 顶层 TLS 封装 | `TlsSocketEndpoint(std::unique_ptr<IceSocketEndpoint>&&, ...)` | ✅ **只接受 `IceSocketEndpoint`** | `peer_connection.h:93,99` |
| **底层 TLS 引擎** | `TlsSession(std::unique_ptr<SocketType>&& transport, ...)`，`SocketType = GenericSocket<uint8_t>` | ❌ **接受任意 `GenericSocket<uint8_t>`** | `tls_session.h:105,125` |
| 通道复用 socket | `ChannelSocketInterface : GenericSocket<uint8_t>` / `ChannelSocket` | ❌ 是泛型 socket | `channel_socket.h:56,130` |
| ICE 端点 | `IceSocketEndpoint : GenericSocket<uint8_t>` | — | `peer_connection.h:54` |

**关键推论**：`TlsSession` 的传输层是抽象的 `GenericSocket<uint8_t>`，而 `ChannelSocket` 和 `IceSocketEndpoint` 都满足这个接口。因此路线 A 的可行路径是——

1. A、B 各自与中继 C 建立**标准 Jami 设备连接**（ICE+TLS，这条已验证可通，C 有公网地址），即 A↔C、B↔C 两条底层连接；
2. 在 A↔C 连接上开一条 **channel**（ADR-002 多通道），作为"到 C 的转发管道"；
3. **绕过 `TlsSocketEndpoint`**，直接用底层 `TlsSession` 把 A↔B 的端到端 TLS 跑在这条管道上（A 的 `TlsSession` transport = A→C 的 `ChannelSocket`；B 侧同理）；
4. C 只做 channel 级**字节搬运**（把 A 的 channel 字节转给 B 的 channel，反之亦然），C 的 TLS 会话终止在 A↔C、B↔C 外层，内层 A↔B 的 `TlsSession` 对 C 不可见 ⇒ **C 只见密文**。

**仍需解决的真实难点**（诚实清单，非已验证部分）：

| 难点 | 说明 | 状态 |
|---|---|---|
| 内层 TLS 证书校验 | A↔B 内层 `TlsSession` 需拿对方证书做 `cert_check`；证书从哪来（好友已交换 / 经 C 透传）须定 | 待设计 |
| C 的转发规则 | C 凭什么把某 channel 的字节转给谁：需要会话 ID + 路由表（谁→谁） | 待设计 |
| 通道协商三方化 | 现有 channel 是两端点对点（`ChannelSocket` 绑定单一 `deviceId`），三方透传需扩展 | 待设计 |
| 双层 ICE/TLS 开销 | A↔C、B↔C 各一层，再叠 A↔B 一层，三握手的延迟与 MTU | 待实测 |
| 与 `announce()`/fetch 语义兼容 | 内层 TLS 上跑 `im-gitmessage-id` 便条 + git fetch，须验证 swarm 层不假设"直连对端" | 待验证 |

> 判定：路线 A **不是死路**——底层 `TlsSession` 的泛型 transport 是关键突破口；但"三方 channel 透传 + 内层证书校验"是真正的新增工作量，属核心难点，不可低估。**本轮只做只读源码核准，未改任何代码。**

## 5. 实现方案（分层，待第 7 章拍板后细化到伪代码级）

| 层 | 职责 | 关键机制建议 | 依赖 |
