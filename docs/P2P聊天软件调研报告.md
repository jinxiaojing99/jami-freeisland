# 去中心化（P2P）聊天软件调研报告

调研时间：2026-11-01 ｜ 目标约束：无中心服务器（可用免费公共服务、不可依赖）、通讯安全、高性能、大规模、中国+全球可用、抗封锁（网络完全中断除外）

---

## 一、结论先行

1. **没有任何一个现有项目完全满足全部六项要求**。最接近的是 Briar（抗断网最强）和 Jami（最活跃的 P2P 栈），但二者都缺"大规模+高性能"；Nostr/Session/SimpleX 缺"中国可用性"或"真正去中心化"。
2. **技术上的核心矛盾是三角权衡**：去中心化（抗封锁）↔ 元数据隐私（安全性）↔ 异步可达性（性能/体验）。纯 P2P 直连没有离线消息；引入中继节点就能被封锁；做洋葱路由性能就下降。现有项目都在这个三角上各自放弃一个角。
3. **在中国，NAT 穿透是最硬的骨头**。2025 年 IPFS/libp2p 实测（440 万次穿越、167 国）全球洞穿成功率约 70%，而中国移动/联通 4G/5G 大量使用对称型 NAT + CGNAT，UDP 洞穿接近失败；GFW 又具备 SNI 过滤、JA3 指纹、熵/时序 ML 分类、主动探测能力（2025 年 8 月曾大规模封 443 端口）。因此"纯 UDP P2P 协议"在中国裸奔几乎不可用，**必须把流量伪装成 WebRTC/WebSocket/HTTPS 形态**。
4. **可行的自建路线**：libp2p（传输/NAT 穿越）+ Signal 协议（1v1，含 PFS/PCS）+ MLS（群组）+ 分层中继（设备自主中继为主、可选 443 端口 HTTPS 中继兜底）+ 免中心命名层。这是目前工程上最现实、且每一层都有经过审计的组件的方案。

### 关键判读

- **"无中心服务器"没有严格意义**：Tox 的 bootstrap、Jami 的 OpenDHT、I2P 的 floodfill、SimpleX 的操作员、Session 的质押节点，都是事实上的关键少数节点。区别只在于：被关掉是"暂时降级"还是"服务死亡"。
- **纯 P2P 的先天缺陷是"双方同时在线"**：Tox/Jami 离线收不到消息；Briar 靠"双方都上线时同步"或 mesh 逐跳扩散（分钟到天级）。要做到"微信级可达性"，**必须引入某种异步信箱（mailbox/relay）**——这一步必然让"无中心"退化为"无唯一中心"。
- **加密安全性梯队**：Signal 协议（PFS+PCS，事实标准）> MLS（群组标准，2023 成为 IETF 标准，明确不提供否认性）> NaCl 静态方案（Tox，无 PFS）> NIP-17（否认性被击穿）。

## 三、关键技术难题与实证数据

### 3.1 NAT 穿透（最大瓶颈）

- libp2p 的 DCUtR 协议（经中继协调双方同时外拨）是全球最佳实践。arXiv 2510.27500（2025-10）基于 IPFS 生产网络 **440 万次穿越、8.5 万网络、167 国** 的测量：洞穿成功率 **70%±7.1%**，TCP/QUIC 无显著差异，97.6% 成功在首次尝试。
- 该数字在中国要打折：住宅/移动 CGNAT 下成功率显著更低，对称 NAT 基本只能走中继。
- 结论：**直连是主路径，中继是必选兜底，不能只赌洞穿。**

### 3.2 GFW 对抗（决定中国可用性）

GFW 能力清单（2025 年状态）：BGP 黑洞、DNS 污染/DoH 识别、SNI 过滤、JA3/JA3S TLS 指纹、包大小/熵/时序的 ML 分类、主动探测（对 Tor 桥数分钟内定位封禁）、2025-08-20 443 端口大规模封锁、按机房 IP 段（OVH/Hetzner/DigitalOcean）DPI 规则。

由此推导的硬约束：

1. **裸 UDP 自研协议流量 = 最容易被熵/时序特征识别的流量**（Tox 模式在中国高风险）。
2. **伪装成"普通 Web 行为"是当前存活率最高的形态**：WebRTC（视频会议流量，封它代价太大）、WebSocket-over-443 到知名 CDN 域名（NaiveProxy/meek 思路）、QUIC。WebTunnel 的短暂成功验证了 443+WebSocket 仍有窗口期，但"窗口期"本身会被缩短。
3. **节点/中继的选址比协议更重要**：住宅 IP、CDN 边缘、轮换域名（DNS 轮换 + 证书轮换）的存活时间远超机房 IP。Session 用代币激励节点分散到 50 国，是节点抗封锁的正确方向（但代币合规是中国的额外约束）。
4. **中国用户与海外用户之间**：GFW 主要影响中国一侧的出口，只要中国侧有可用入口（443 伪装/CDN），跨国通信本身不增加难度。

### 3.3 元数据与大规模群组

- 1v1：Signal 协议（X3DH+Double Ratchet）是安全上最省事的选项，含 PFS+PCS。
- 群组：MLS（RFC 9750）是唯一经过审计的大规模群组 E2EE 方案，密钥更新 O(log n)；但每消息带签名 → **可证明"发过"**（放弃否认性换滥用可追责，RFC 明示）。
- 元数据（谁和谁、何时）：纯 P2P 直连天然暴露双方 IP（Tox 明示）；保护手段是洋葱多跳（Briar/Session 模式，代价是延迟+中继容量）。**完全消除元数据与低延迟不可兼得**，需按用户敏感度分档：普通模式（直连，低延迟）/ 隐私模式（2-3 跳，抗关联）。

### 3.4 断网兜底（"网络完全中断除外"的边界内红利）

- Briar 验证了 Wi-Fi/蓝牙 mesh 的可行性，但 iOS 做不了蓝牙 mesh（系统限制）。
- 自建时建议把 LAN 发现（mDNS/UDP 广播）作为可选模块：局域网断外网时仍可通（Jami 已实现，可直接借鉴）。

## 五、推荐架构（自建路线）

分层设计，每层选已被验证的组件，自研只做"胶水"：

```
┌─────────────────────────────────────────────────────────┐
│ 应用层：IM（1v1 / 群组 / 文件）                            │
├─────────────────────────────────────────────────────────┤
│ 消息层：Signal 协议（1v1，PFS+PCS）                        │
│         MLS（群组 ≤1000 人，O(log n) 密钥更新）             │
│         离线信箱：绑定在"信箱中继"上的加密队列（可选开启）    │
├─────────────────────────────────────────────────────────┤
│ 隐私层（可选/分档）：                                      │
│   普通模式 = 直连（低延迟）                                 │
│   隐私模式 = 2-3 跳随机中继洋葱路由（抗关联，抗 IP 暴露）    │
├─────────────────────────────────────────────────────────┤
│ 传输层：libp2p                                            │
│   主：QUIC/UDP 直连 + DCUtR 洞穿（全球 ~70%）              │
│   备 1：WebRTC DataChannel（伪装视频会议流量，中国可用率高） │
│   备 2：WebSocket/443 到轮换 CDN 域名（抗 GFW 窗口期方案）  │
│   兜底：LAN mDNS/蓝牙（断外网局域网通信，参考 Jami/Briar）  │
├─────────────────────────────────────────────────────────┤
│ 发现/路由层：                                             │
│   Kademlia DHT（用户身份=公钥，身份即寻址，无注册）          │
│   bootstrap 多源：内嵌轮换节点 + DNS 轮换域名 + 用户互换快照 │
│   自主中继（autonomous relay）：任意用户设备可开，          │
│   容量受限、加密穿透不可读（IPFS relay v2 模式）            │
├─────────────────────────────────────────────────────────┤
│ 命名层（可选）：公钥 → 人类可读名字的分布式映射，            │
│   避免单点（可参考 Nostr NIP-05 思路但换成可去中心化目录）   │
└─────────────────────────────────────────────────────────┘
```

**设计决策与理由**：

1. **libp2p 做传输底座**：它是唯一同时具备 QUIC/UDP/TCP/WebRTC、DCUtR 洞穿、autonomous relay、Noise 加密的成熟栈（Go/Rust/JS/Swift 多语言实现），Berty/Status 已证明其可承载 IM。
2. **Signal+MLS 做消息层**：安全审计历史最长；自研加密协议是这类项目最常见的翻车点，坚决不自研。
3. **可达性问题用"加密信箱"解决**：这是所有纯 P2P 方案（Tox/Jami/Briar）的体验死穴。信箱 = 用户选择信任的若干"信箱中继"（可自托管），存密文队列；中继不知道内容、不知道会话对象（双 ECDH 寻址）。代价：引入可选依赖的节点——但按你的要求"可以用免费服务、不可依赖"，信箱中继恰好符合：没有它只是收不到离线消息，系统本身不依赖任何单一实体。
4. **中国可用性押注在 WebRTC/443-WebSocket 伪装层**：这是 2025 年数据里唯一仍被验证"能进"的形态（WebTunnel 短暂成功、snowflake 的 WebRTC 思路在俄/伊存活）。纯 UDP 协议在中国必须当备胎。
5. **抗封锁靠节点形态而非协议签名**：中继节点用住宅/CDN/轮换域名，流量形态模仿 WebRTC/HTTPS，证书与域名轮换。Session 的"节点地理分散"策略 + I2P 的"人人可路由"策略是已验证方向。
6. **诚实的性能预期**：
   - 直连模式：RTT 即物理延迟，文字消息 <500ms（同地区）；
   - 隐私模式（2-3 跳）：秒级，消息可达延迟 1-10s；
   - 信箱离线补发：取决于信箱中继在线率，分钟级；
   - 群组（MLS，100 人）：每消息加解密与成员数对数相关，移动端可接受；
   - 与微信（200-500ms 全球）相比，文字聊天体验在直连模式可追平，在隐私模式不可追平。

**工程量与里程碑建议**（如老板决定自研）：

| 阶段        | 内容                                             | 出口标准                |
| --------- | ---------------------------------------------- | ------------------- |
| M1（4-6 周） | libp2p 节点 + QUIC 直连 + 基础 DHT + 1v1 Signal 加密文本 | 两台机器跨 NAT 互发加密消息    |
| M2（4-6 周） | DCUtR + autonomous relay 兜底 + WebRTC 传输通道      | 对称 NAT 设备可互通（直连或中继） |
| M3（6-8 周） | 443-WebSocket/CDN 伪装传输 + DNS 轮换 + 中国侧实测        | 中国大陆普通网络可稳定收发消息     |
| M4（6-8 周） | MLS 群组 + 文件传输 + 离线信箱                           | 100 人群 E2EE 群聊；离线补发 |
| M5        | 客户端打磨（移动端）、威胁模型审计、可选蓝牙/LAN mesh                | 第三方安全审计通过           |

## 六、风险提示（不可回避）

1. **合规风险（中国）**：运营任何加密通信服务在中国都面临《网络安全法》/《密码法》下的合规压力；"抗审查"设计本身在国内宣传即高风险。Session 的代币激励方案在中国不可复制。
2. **"抗封锁"是军备竞赛不是终点**：WebTunnel 存活数周到数月的先例说明，443 伪装方案有窗口期衰减，需要持续投入对抗迭代；不存在"一次做到不怕封锁"。
3. **用户增长是生死线**：Berty、Tox、Briar 的轨迹一致——技术再对，没有用户群就没有 DHT 节点密度、没有中继容量、没有洞穿成功率。冷启动建议先做"小圈子内完全替代"（组织/团队内部），再谈全球。
4. **若只想"用"不想"建"**：最务实的组合是 **Jami（主力，活跃+跨平台）+ Briar（断网/高敏感场景备用）+ 自部署 Tor 桥或 I2P（兜底通道）**，接受其离线消息与性能妥协。
