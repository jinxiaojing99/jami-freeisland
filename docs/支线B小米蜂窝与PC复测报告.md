## 三、判定缺陷修复（关键改动）

**原逻辑（有缺陷）**：`handle()` 收到 `S` 包就 `markEst(idx, "S_LINK")`。

- 问题：收到对方的 S 只证明"对方打到了我"，**完全不能证明我的回包能到对方**（对方 NAT 可能严格丢包）。却把它计入 `EST`，使 `RESULT=HIT` —— 单向命中被误报成"打通"。

**修复后**：

```
收到 S  → 记录 S_RECV，在同一 socket 回 SA（带双方端口），但不 markEst
收到 SA → 才 markEst(SA_LINK)   // 对方确认在我映射源端口收到我的包 = 真双向
```

| 口径  | `RESULT=HIT` 的含义                  |
| --- | --------------------------------- |
| 修复前 | 只要收到过对方一个 S 包（可能单向）               |
| 修复后 | 至少一条 socket 完成 SA 双向确认（`SA_LINK`） |

自检结果（`selftest_safix.log`）：`[A/PC] RESULT=HIT EST=8`、`[B/PHONE] RESULT=HIT EST=8`，全部 `SA_LINK`、`foreign=0` —— 修复不影响真双向的判定。

## 五、为什么 STUN 块中心±512 打不中

N×M 全交叉的理论前提是：socket 的 NAT 映射源端口 `p`，在只改变目的端口（目的 IP 不变）时保持稳定（ADM）。若真如此，把对端窗口取"STUN 测得的映射块中心±512"应能覆盖 `p`。

但本轮 PC 的 STUN 映射块是 `5252–5295`，手机 sprayed 的窗口 `4762..5785` **完整覆盖了它**，手机却 `RECV=0`。这说明：

- **STUN 服务器方向得到的映射端口 ≠ 打向对端方向时的映射端口**。NAT 是**按目的地址/端点分配映射**的（ADM + 按目的分配），对 `stun.l.google.com` 分配的端口，与对 `198.51.101.141` 分配的端口不在同一块。
- 这也解释了历次实验的现象：此前唯一一次 PC→手机单向命中（手机 RECV=21），是 PC 打向手机时分配的源端口（5234/5235/5378）**碰巧**落进了按 STUN 块算出的手机窗口；本轮这个巧合没有重现。
- 没有第三方可观测点能提前知道"打向对端时"的映射端口 ⇒ 鸡生蛋问题，喷洒路线无法闭环。

这正是 §8.9~§8.16 反复印证的结论，本轮在严格判定口径下再次确认。

**进一步精确判定（§8.18，同日补测）**：用 `NatMapProbe.java` 让**同一 socket** 发往同一 STUN IP（`74.125.250.129`）的不同端口（19302 vs 3478），实测 **PC=ADM（11/12 映射端口不变）、小米蜂窝=Symmetric（12/12 映射端口全变，发 19302 落 13xxx–14xxx、发 3478 落 38xxx 两个不同端口池）**。⇒ 即使代码复用收包 socket 回包，手机 CGNAT 也会按新目的端口重分配映射源端口，PC 严格 tuple 过滤丢包。**"复用 socket"无法对抗 Symmetric NAT**——这是"手机收到包、PC 收不到回包"的物理根因，非代码所能改变。
