# 专题研究：I2P 与 Jami 在中国使用的问题及方案缺陷

调研时间：2026-11-01 ｜ 基于 I2P 论坛中文/英文用户报告、官方文档、net4people 问题追踪、Jami 官方架构文档

---

## 一、I2P 在中国使用的问题（按严重度排序）

### 1.1 冷启动问题：reseed 服务器全部被墙（结构性硬伤）

- I2P 节点首次启动需要向 reseed 服务器拉取网络数据库（netDb，一个 .su3 文件，含全网络路由器列表）。
- **中文维基教科书（长期维护）明确记录："目前 I2P 播种服务器均被封锁"**——官方默认 reseed 列表（reseed.i2p.rocks、reseed-fr.i2pd.xyz、i2p.novg.net、i2p-projekt.de）在中国大陆全部不可达。
- 官方故障排除文档自己给出的"重度审查地区"建议是：用 Tor 桥接做初始 reseed，或通过 steganography/邮件/U 盘/朋友拷贝 su3 文件。**"找朋友要一份补种文件"本身意味着该网络已把"可信的既有用户"当成入场券**——这对一个"抗封锁"网络是根本性的冷启动缺陷。
- 实际后果：新用户无法独立加入，必须依赖中国境内已有 I2P 用户的"人际传播"。

### 1.2 运行期问题：持续被干扰（2025 年 6 月事件 + 慢性退化）

I2P 论坛用户 656pppqqq（2024-09 起使用，至 2025-09 持续报告）的时间线：

| 时间 | 事件 |
|---|---|
| 2025-06-29 | 突发：先无法访问 http 站点，随后 .i2p 站点也大面积失效 |
| 2025-07-05 | http 出口恢复，但 .i2p 站点基本不通；客户端"经常被强制 reseed"，需频繁重启 |
| 2025-08 | 开发者 zzz 称花一个月修 hidden mode 问题，2.10 版（09-08）应大幅改善 |
| 2025-09-08 | 升级 2.10，**头一周非常好，无 reseed 问题** |
| 2025-09-16 | 再次突发失效，reseed 失败比之前更严重，Mac 端持续至今；Windows i2p+ 靠自制 reseed bundle 勉强可用 |

判读：

1. **干扰呈"脉冲式"而非一次性封锁**——说明 GFW/运营商不是把 I2P 协议特征永久加入黑名单，而是周期性扫描 + 对可疑节点 IP 段（机房 VPS 为主）做动态封禁。9-08 到 9-16 的一周好光景，与 2.10 修复后行为变化吻合，但随后又恶化，说明对手在持续调整策略。
2. **中文论坛生态本身在萎缩**：i2pforum 中文区 2025 年帖子稀疏，"大量中国节点隧道"、"出口节点都不能用了？"等帖反映中国用户参与度在下降——网络内中国节点越少，中国用户可直连的 peer 越少，可用性越差（恶性循环）。
3. 官方文档承认的现实预期：工作正常的 I2P 路由器 = **30 秒加载一个网页、50KB/s 的下载速度**。这对"聊天软件"是致命的——文字消息勉强可用，文件/语音/视频基本不可用。

### 1.3 协议层问题：NTCP2/SSU2 的"高熵随机"策略在中国是双刃剑

I2P 开发者的官方立场（论坛 2025-01，zzz）：

- I2P 不走 Tor 的"伪装成别的东西"路线（pluggable transports），而是走"所有字节都随机化、无可识别特征"路线（NTCP2 用 SipHash 混淆帧长，SSU2 全随机）。
- 开发者自称"很少收到封锁报告"——**但中国是明确的反例**（上面的 2025-06 事件）。
- 这个路线的内在缺陷：**"看起来像随机垃圾"恰恰是高熵流量检测（entropy-based ML classifier）的目标特征**。GFW 自 2021 年部署基于 ML 的被动检测，专门标记"高熵、无结构"的加密流量。I2P 的设计哲学（"不像任何合法流量"）与 GFW 当前最有效的检测手段（"找不像任何合法流量的"）正好对撞。
- 对照：Tor 的 obfs4 也是高熵策略，2025 年在中国同样被大规模封禁——两条路线在中国殊途同归地失效。
- **关键缺失：I2P 没有 WebRTC/443-WebSocket 这类"伪装成合法常见流量"的传输选项**。NTCP2 走 TCP 任意端口（默认 1155），SSU2 走 UDP（默认 30000+），都不是 443。这意味着在 GFW 已封死 443 伪装窗口收窄的环境下，I2P 没有任何"合法外衣"可用。

### 1.4 NAT 与 ISP 行为问题：最容易被忽视的杀手

net4people/bbs issue #583（2026-02，河南联通 5G+宽带，多地可复现）记录的未知 ISP 行为：

> 当 P2P 软件使用 **TCP** 连接（如 I2P 的 NTCP）时，运行一段时间后，**该用户线路的所有出海 TCP 连接被静默丢弃**（握手被 drop 而非 RST）——不只是 I2P，连正常的海外网站都打不开。只有 UDP 的代理（如 Xray-Reality、SS-over-HTTP）幸免。
> 反过来，如果 P2P 软件走 **UDP**（如 I2P 的 SSU），则触发反向行为：**所有出海 UDP 包被丢弃**，TCP 代理正常。
> 恢复方法：重启光猫/路由器，或 PPPoE 重新拨号。

这一发现对 I2P 是决定性的：

1. I2P 同时跑 NTCP（TCP）和 SSU（UDP）双传输来"提高穿透率"——**在触发该 ISP 行为的线路上，这等于把两条出海通道都点了火**：TCP 方向被断后，UDP 方向的 SSU 也可能被连带标记，或反之。
2. 触发条件是"连接大量境外 IP + 大流量"——I2P 的 router 默认会建立数十条到数百条到全球 peer 的隧道，**是教科书级的触发画像**。
3. 该行为无法用"PCDN 打击"解释（境内 P2P 不受影响，只断出境方向），且江苏、河南等省已复现，江苏的 4G/5G 移动网络"触发得特别快"。
4. **I2P 的"多传输、多路径"设计哲学在这里从优点变成缺点**：传输越全面、连接越多、流量越大，被 ISP 侧异常检测系统标记的概率越高。
5. 对"聊天"用途的直接后果：用户开着 I2P 聊天客户端，自己的整条线路可能连普通网页都上不了——**软件在"保护用户"的同时"伤害了用户自己的网络"**，这是产品级的缺陷。

### 1.5 架构缺陷清单（超出中国场景的通用问题，但在中国放大）

| 缺陷 | 说明 |
|---|---|
| **reseed/floodfill 是关键少数节点** | 官方 4 个 reseed 全被墙；floodfill 路由器被干扰即全网发现能力退化。"去中心化"叙事与冷启动现实矛盾 |
| **网络规模对中国用户不利** | 全球约 4-5.5 万路由器，中国节点占比小且持续下降；中国用户建隧道时大部分 peer 在境外，RTT 高且易被干扰 |
| **性能与 IM 需求不匹配** | 设计目标是匿名浏览/文件共享（50KB/s 算正常），不是低延迟 IM；garlic routing 12 跳（6+6）的固有延迟使实时聊天体验差 |
| **没有 IM 原生应用** | 聊天依赖 I2PBote 等第三方，群聊/离线消息/多设备同步均无 |
| **移动端能力弱** | 无官方 Android/iOS 客户端，靠 i2pd 自编译或第三方（I2P 1.9 ARM 版官方长期不更新，"抗封锁能力最差"） |
| **出口代理单点** | 访问 clearnet 依赖少数几个公共出口代理（exit.stormycloud.i2p、purokishi.i2p），中文社区多次报告出口节点失效 |

## 二、Jami 在中国使用的问题（按严重度排序）

### 2.1 结构性依赖：Jami 不是"无服务器"，是"五个可自建的服务器"

Jami 官方页面（jami.net/why-is-jami-truly-distributed）自己承认，以下 5 处仍需服务器：

1. **Bootstrap 节点**：默认 `bootstrap.jami.net:4222`（Savoir-faire Linux 维护，TCP 4222 端口）。首次入网/缓存失效时**必须**连上它。
2. **Name Server**：默认 `ns.jami.net`（HTTP 服务，Savoir-faire 维护），名字解析走它；底层是 **Ethereum 私有链**（JamiNS，网络 ID 1551），名字注册写在链上。
3. **OpenDHT Proxy**：移动端推送通知需要这个代理服务器监听 DHT 变化并经 APNs/FCM 下发。
4. **TURN 服务器**：NAT 穿透失败时的官方默认中继。
5. **通知推送**：依赖 Google FCM / Apple APNs——**这两家在中国境内都不稳定/不可用**（FCM 被墙多年，APNs 走 443 通常可用但 FCM 是 Android 的硬依赖）。

判读：

- 每个组件都"可自建替换"，但**默认值全部指向 Savoir-faire 一家公司维护的节点**。在中国：
  - `bootstrap.jami.net:4222` 是非标准端口的加密 TCP 长连接——**典型的容易被 DPI 标记的流量画像**（非 443 端口 + 高熵 + 长连接），且没有混淆选项；
  - `ns.jami.net` 是明文 HTTP（注意：官方文档里就是 `http://` 而非 https），域名被解析/封锁即名字功能全灭（ID 直连仍可用）；
  - **FCM 在中国基本不可用** → Android 端后台推送失败 → 消息/来电无法唤醒应用 → "对方不在线就收不到"的问题在中国 Android 上会被放大成常态。
- 官方"你可以自建全部五个服务器"的承诺，对一个普通用户意味着：租海外 VPS + 自跑 dhtnode + 自跑 Ethereum 节点 + 自跑 TURN + 自跑 OpenDHT proxy，**"去中心化"的成本转嫁给了每一个想要完全自治的用户**——这在实际中等同于"该网络对普通用户是中心化的"。

### 2.2 NAT 穿透：标准 ICE，在中国网络下成功率存疑

- Jami 用 **ICE**（STUN + 主机候选 + TURN 兜底）建立 P2P TCP 直连，而非 libp2p 的 DCUtR 或 I2P 的 SSU2。
- ICE/STUN 的经典弱点：对称 NAT（Symmetric NAT）下洞穿失败率接近 100%，必须走 TURN。中国移动/联通 4G/5G 的 CGNAT + 对称 NAT 占比高，意味着**相当比例的中国移动用户会退化成"经官方 TURN 中继"模式**——此时 Savoir-faire 的 TURN 服务器成为事实上的必经之路，"无中心"进一步塌缩。
- ICE 走 TCP 长连接 + 任意端口（默认 4222/4443 等），同样缺乏 443/HTTPS 伪装选项。
- 对照数据：libp2p DCUtR 全球洞穿成功率 70%±7.1%（2025 实测），但中国 CGNAT 环境下应显著更低；Jami 没有任何公开的中国场景实测数据。

### 2.3 流量特征与可识别性

- OpenDHT 的 Kademlia 协议流量：加密的 UDP/TCP 消息，固定网络 ID 0（公网大网），节点间定期 ping 维持 DHT 结构——**行为模式高度可识别**（周期性、低速率、大量小消息、多对多），与"合法 Web 流量"形态差异极大。
- 没有 pluggable transport 机制、没有 WebRTC 通道、没有 443 伪装。Jami 的抗审查叙事停留在"无中心服务器所以没法封"——**但 GFW 不需要封服务器，它可以直接封协议特征/封用户线路**（I2P 案例已经证明）。
- 一个更现实的威胁：Jami 用户在中国跑 DHT 节点 = 持续的出海 UDP/TCP 小流量 = 与 I2P 案例 #583 描述的"P2P 触发 ISP 出境封锁"画像高度重合（虽然 #583 主要指大流量 P2P，但 DHT 维持流量的多对多长连接同样异常）。

### 2.4 用户规模与生态缺陷

- Jami 全球用户基数很小（相对 Signal/Telegram 可忽略），在中国**几乎没有用户群**。P2P 聊天软件的价值完全取决于"你的朋友也在用"，Jami 在中国的用户密度使它在实用意义上不可用。
- 移动端（尤其 iOS）需要常驻前台或依赖 FCM/APNs 保活，耗电与可达性问题与 Tox/Briar 同类。
- 项目活跃（2025-09 Atlas 版、2026-04 Euclid 版），但 roadmap 聚焦功能丰富度，**没有任何针对审查环境的专项工作**（无混淆传输、无中国/伊朗/俄罗斯用户反馈渠道的公开记录）。

### 2.5 架构缺陷清单

| 缺陷 | 说明 |
|---|---|
| 5 个隐性中心点，默认值全指向同一公司 | bootstrap / name server / proxy / TURN / push，"去中心化"是架构能力而非默认现实 |
| 名字系统依赖 Ethereum 私有链 | 注册名字要付 gas 费；链节点资源门槛高；ns.jami.net 是 HTTP 明文 |
| 移动端推送依赖 FCM/APNs | 中国 Android 的 FCM 不可用，离线消息/来电唤醒严重退化 |
| ICE 洞穿，无 DCUtR 级机制 | 对称 NAT 下依赖 TURN，而官方 TURN 是中心化节点 |
| 无流量混淆选项 | 4222 端口长连接 + 高熵，DPI 友好型特征 |
| 无中国实测/无中文社区 | 所有中国可用性问题都是"未验证"，等于默认不可用 |
| 用户基数小 | P2P 网络效应缺失，实用性为零 |

## 三、两个方案缺陷的共性与对照

| 维度 | I2P | Jami | 共性结论 |
|---|---|---|---|
| 冷启动 | reseed 全被墙，需人际传 su3 | bootstrap.jami.net 单点（可自建但门槛高） | **两者都存在"关键少数节点"，且默认值在中国都不可达或高危** |
| 流量伪装 | 无（全随机高熵路线） | 无（4222 加密长连接） | **都选择了 GFW 时代最容易暴露的"高熵裸奔"路线，缺乏 WebRTC/443 伪装层** |
| NAT 穿透 | SSU2 洞穿 + firewalled 降级 | ICE 洞穿 + TURN 兜底 | 都支持，但中国 CGNAT 下成功率均存疑，且 Jami 会退到中心 TURN |
| ISP 侧风险 | 双传输多连接 → 触发"出海 TCP/UDP 全断"行为（已实证） | DHT 多对小连接 → 同画像，未实证但风险同构 | **多对多 P2P 行为本身就是触发条件，"去中心化节点越多越安全"在中国 ISP 环境下不成立** |
| 性能 | 30s/页，50KB/s（官方预期） | 直连时低延迟，但群规模小、无实测 | 都达不到"微信级体验" |
| 中国用户生态 | 存在但萎缩（2025 论坛冷清） | 几乎为零 | 都没有"中国节点密度"，可用性随用户下降而下降 |
| 移动端 | 无官方移动客户端 | 有，但 FCM 不可用伤及推送 | 都难以支撑日常移动聊天 |

**核心判断**：

1. I2P 的问题集中在"**网络层被针对**"——reseed 封锁、2025-06 起的周期性干扰、ISP 触发断网，三者叠加使其在中国从"可用但慢"退化为"需要手动维护、随时可能失联"。
2. Jami 的问题集中在"**架构默认值全部不在中国**"——不是协议被识别的问题，而是它默认依赖的 5 个组件 + FCM，每一个在中国都是不可用或高危的，需要用户全部自建才能"理论上可用"。
3. 两者共享的深层缺陷：**都默认"加密高熵流量 + 非常规端口"是可行的传输形态**。2024-2025 年 GFW 的实战记录（obfs4/Tox 式流量全部失效、WebTunnel 短暂有效）已经证明这个默认假设在中国不再成立。**任何在中国可用的 P2P 聊天方案，必须把"伪装成 WebRTC/WebSocket/HTTPS 的常见流量"作为一等公民传输通道，而不是可选项**——这是 I2P 和 Jami 都没有做的，也是上一份报告中推荐架构把 WebRTC/WSS-443 列为必选通道的原因。

## 四、若仍要在 I2P/Jami 上"用"的现实建议

**I2P**：
1. 首次 reseed 必须从境内可信用户获取 su3（官方建议 steganography/离线传输）；自己会做 reseed bundle 后尽量只用自制 bundle。
2. 限制带宽（默认值会触发 ISP 异常检测），降低并发隧道数；接受 firewalled 状态。
3. 把它定位为"**备用暗通道**"（访问 .i2p 站点、与特定联系人走 .i2p 地址），不要当日常聊天工具；聊天用它时预期延迟秒级、消息需双方在线。
4. 监控 2.10 之后的版本行为（开发者在针对中国场景修 hidden mode 问题），但要有"再次恶化"的心理准备。

**Jami**：
1. 在中国使用前先实测三件事：`bootstrap.jami.net:4222` 可达性、官方 TURN 可达性、Android 端 FCM 是否工作。
2. 预期要自建：至少 bootstrap + TURN（可先借社区节点，长期自跑 dhtnode + coturn）。
3. 名字系统可弃用（直接用 40 字符 ID），规避 ns.jami.net 与 Ethereum 依赖。
4. 把它定位为"**小圈子全平台通话工具**"（跨 Windows/macOS/Linux/iOS/Android + 音视频 + 局域网可用），不适合在中国作主力。

**结论**：两者都不建议作为"中国+全球"场景的主力聊天方案；I2P 可作为高敏感场景的兜底匿名层，Jami 可作为小团队跨平台通话的备选。主力方案仍应回到上一份报告的分层自建架构（libp2p + WebRTC/443 伪装通道 + Signal/MLS）。

| 3 | §2.1 / 来源：「自建需自跑 Ethereum 节点（网络 ID 1551）」 | 当前名称服务是 HTTPS REST，源码中**未见 Ethereum 强依赖**；`managerUri` 是可选的 JAMS 管理服务器，不是入网必需 | `namedirectory.cpp`；`jamiaccount_config.h:70-71` |

| 上文结论 | 复核 |
|---|---|
| 「Jami 不是无服务器，是一组默认指向同一公司的可自建设施」 | ✅ 成立。补齐为 6 类：bootstrap / 引导列表 / 名称服务 / DHT proxy / TURN / 推送，全部有对应配置项可替换 |
| 「中国 CGNAT/对称 NAT 下退化到官方 TURN」 | ✅ 成立。**补一句**：TURN 转发的是已经端到端加密的 TLS 字节流，不是聊天明文，也不是消息落地节点 |
| 「FCM 不可用放大 Android 后台收不到消息」 | ✅ 成立。桌面端不涉及推送 |
| 「广域网冷启动结构性依赖外部引导」 | ✅ 成立。ICE 信令（`putEncrypted(InfoHash("peer_request"+deviceId), …)`）、好友请求、设备证书查询全都要靠 DHT；DHT 起不来就不知道该连谁 |

**新增关键结论**：官方设施**没有一台承载聊天内容或建连信令服务器**——ICE 候选交换走 DHT 加密值（`dhtnet/connectionmanager.cpp:755-788`），消息正文走 TLS 命名通道（ADR-002）。所以「封域名」不等于「封网络」：局域网自组、老用户缓存续用、自建 bootstrap/TURN 都是现成能力，**不需要改 Jami 代码**。真正卡死的是「DHT 网络整体不可达」。
